# Формат карточек (контракт viewer ↔ filler_bot)

Этот файл — единый источник правды для обоих проектов. Изменения формата нужно
синхронизировать между `git_web` (viewer) и `filler_bot` (бот).

## Расположение

```
git_web/                 <- корень репозитория (GitHub Pages)
├── index.html           <- viewer
├── css/, js/            <- код viewer'а
└── cards/               <- карточки (md-заметки)
    ├── index.json       <- индекс всех карточек
    ├── hieroglyph-1.md
    └── rule-1.md
```

## Файл карточки

Одна карточка = один `.md` файл в `cards/`.

Имя файла: `<type>-<номер>.md`, где `номер` — положительное целое, уникальное
внутри типа: `hieroglyph-1.md`, `hieroglyph-2.md`, `rule-1.md`. Номер не должен
намекать на содержимое: имя файла видно в адресной строке, поэтому имена вроде
`hieroglyph-你好` не используются. Бот берёт первый свободный номер для типа;
существующая карточка при этом не перезаписывается.

### Структура

YAML-frontmatter (служебные поля) + тело с секциями `## Поле` (контент карточки).

Служебные поля frontmatter:

| поле    | тип    | обязательное | описание                                              |
|---------|--------|--------------|-------------------------------------------------------|
| `type`  | string | да           | `hieroglyph` или `rule`                               |
| `lesson`| int    | да           | Номер урока                                           |
| `level` | string | да           | Уровень, свободный текст (`HSK1`, `HSK3.0`, ...)      |

Поля `title` нет: название, указывающее на содержание, подсказывало бы ответ при
повторении с закрытой стороны. Подпись карточки («Иероглиф 7», «Правило 2»)
viewer строит сам — по типу и позиции карточки в `index.json`; в md и в индексе
она не хранится.

**Поля, связанные с пользователем (когда смотрел, как оценил), в md НЕ хранятся** —
только в `localStorage` браузера.

### Карточка «Иероглиф»

Секции тела (в этом порядке):

```markdown
---
type: hieroglyph
lesson: 1
level: HSK1
---

## Иероглиф

你好

## Пиньинь

nǐ hǎo

## Перевод

привет; здравствуйте

## Пример

你好，我叫李明。
```

### Карточка «Правило»

Секции тела (в этом порядке):

```markdown
---
type: rule
lesson: 2
level: HSK1
---

## Правило

Частица 的 ставится между определением и определяемым словом.

## Примеры

我的书 — моя книга
老师的名字 — имя учителя
```

### Правила рендеринга

1. Всё, что идёт после `## Заголовок` и до следующего `##`, — содержимое одного поля
   (многострочное, переносы строк сохраняются).
2. Каждая секция `## ...` — **один спойлер**: при открытии карточки все поля закрыты,
   заголовок секции виден как подпись кнопки-спойлера, содержимое скрыто.
3. Подпись карточки (`Иероглиф 7` / `Правило 2`), `lesson`, `level` видны всегда
   (шапка карточки), спойлерами не закрываются.
4. Текст между frontmatter и первой секцией `##`, если он есть, показывается как
   обычный текст над спойлерами (по возможности не использовать).
5. Секция с пустым содержимым показывается как спойлер с пометкой «пусто».

## Индекс `cards/index.json`

Единственный способ для viewer'а узнать список карточек (GitHub Pages не отдаёт
листинг директории). Порядок элементов = порядок добавления карточек.

```json
{
  "version": 2,
  "cards": [
    {
      "path": "cards/hieroglyph-1.md",
      "type": "hieroglyph",
      "lesson": 1,
      "level": "HSK1"
    }
  ]
}
```

- `path` — путь относительно корня репозитория, без URL-кодирования (viewer сам
  кодирует каждый сегмент через `encodeURIComponent`).
- Дубликаты `path` в индексе не допускаются.
- Подпись карточки — её позиция среди элементов того же `type` (считая с 1).
  Поэтому порядок массива `cards` — часть отображения: у первой карточки типа
  `hieroglyph` подпись «Иероглиф 1», у второй — «Иероглиф 2» и так далее.
- Индекс обновляет бот при добавлении/удалении карточек. Ручное добавление карточки
  требует ручного обновления `index.json` (см. `tools/build_index.py`).

## Пользовательский прогресс (localStorage, только viewer)

| ключ             | где                | содержимое                                                                      |
|------------------|--------------------|---------------------------------------------------------------------------------|
| `cl:v1:user`     | localStorage       | `{"name": "..."}`                                                               |
| `cl:v1:progress` | localStorage       | `{"<path>": [{"ts": 1699999999, "rating": "good"}]}`                            |
| `cl:v1:srs`      | localStorage       | `{"<path>": {"n":1,"ef":2.36,"ivl":1,"due":1699999999,"reps":1,"lapses":0}}`     |
| `cl:v1:session`  | sessionStorage     | `{"mode":"srs","paths":["<path>"],"i":0,"done":0,"requeued":{}}`                 |

`rating`: `bad` | `ok` | `good`. Хранится весь массив оценок (не только последняя),
элементы дописываются в конец.

**Значения оценок в хранилище не меняются.** В интерфейсе они подписаны
«Не помню» / «Слабо помню» / «Хорошо помню», но в `progress` и в файле копии
по-прежнему лежат `bad` / `ok` / `good` — иначе сломается уже накопленная история.

### Интервальное повторение (`cl:v1:srs`)

Упрощённый SM-2, реализация — `js/srs.js` (чистые функции, тесты — `tools/test_js.js`).

| поле     | смысл                                                             |
|----------|-------------------------------------------------------------------|
| `n`      | сколько успешных повторов подряд (сбрасывается в 0 на `bad`)      |
| `ef`     | «легкость» карточки, 1.3 … 3.0, старт 2.5                         |
| `ivl`    | текущий интервал в днях (0 — карточка не выучена)                 |
| `due`    | когда карточка нужна снова, unix-секунды                           |
| `reps`   | всего ответов по карточке                                          |
| `lapses` | сколько раз отвечено `bad`                                         |

- Первый успех — интервал 1 день, второй — 6 дней, дальше `ivl × ef` (не больше 365).
- `bad` сбрасывает `n` и интервал, ставит `due = сейчас` и понижает `ef`: карточка
  возвращается в текущую сессию, но не больше двух раз (`MAX_REQUEUE`).
- `ef` меняется по формуле SM-2: `good` +0.10, `ok` −0.14, `bad` −0.32.

### Резервная копия

Файл копии — это `cl:v1:user` + `cl:v1:progress` + `cl:v1:srs` одним JSON. Сессия
повторения (`cl:v1:session`) в копию не попадает: это состояние вкладки, а не прогресс.

```json
{
  "app": "chinese-cards",
  "version": 1,
  "exportedAt": 1699999999,
  "user": { "name": "Дмитрий" },
  "progress": { "cards/rule-1.md": [{ "ts": 1699999999, "rating": "good" }] },
  "srs": { "cards/rule-1.md": { "n": 1, "ef": 2.36, "ivl": 1, "due": 1700086399, "reps": 1, "lapses": 0 } }
}
```

- Файл с другой меткой `app` или с `version` больше текущей не принимается.
- Импорт «объединить» ничего не теряет: одинаковые записи оценок (один `ts` и одна
  оценка) не удваиваются, из двух расписаний побеждает более продвинутое.
- Имя из файла применяется только к пустому текущему имени.

### Чего в индексе и frontmatter быть не должно

`cards/index.json` собирают два «закрытых» сериализатора — `filler_bot/index.go`
(структура `IndexEntry`) и `tools/build_index.py` (пересобирает ровно 4 ключа).
Новые поля там появятся только после правки обоих. Прогресс, расписание и настройки
viewer'а живут исключительно в `localStorage`.
